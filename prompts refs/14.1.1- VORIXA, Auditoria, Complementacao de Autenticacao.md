# 1. ACCOUNT LINKING

Na Auditoria 14.1 foi identificado:

`allowDangerousEmailAccountLinking: true`

### Verificar

1. Localizar exatamente onde essa configuração está definida.
2. Explicar tecnicamente por que ela está habilitada.
3. Verificar se ela é realmente necessária para o VORIXA.
4. Avaliar o risco de associação indevida de contas.
5. Testar conta criada por Email + Senha e tentativa de login pelo Google usando o mesmo email.
6. Testar conta Google e tentativa de criação/login por Credentials com o mesmo email.
7. Testar email já existente.
8. Testar identidade Google diferente.
9. Verificar se uma conta pode ser associada a outra sem ação explícita e segura do usuário.
10. Verificar se existe possibilidade de tomada de conta através desse comportamento.

### Regra de segurança

Se `allowDangerousEmailAccountLinking: true` não for indispensável, alterar para a configuração mais segura adequada ao projeto.

Não manter essa opção simplesmente por conveniência.

Se a opção precisar permanecer habilitada, documentar claramente:

- motivo;
- risco;
- mitigação;
- comportamento esperado;
- testes realizados.

Criar testes de regressão para o cenário de account linking.

# 2. RECUPERAÇÃO DE SENHA

A Auditoria 14.1 identificou que o fluxo atual de recuperação utiliza comportamento mock.

Não é necessário implementar toda a integração de email nesta etapa.

Porém, a arquitetura deve ficar preparada corretamente.

### Verificar

1. Localizar endpoint de recuperação.
2. Verificar se o sistema permite enumeração de usuários.
3. Verificar geração de token.
4. Verificar se token possui aleatoriedade adequada.
5. Verificar expiração.
6. Verificar uso único.
7. Verificar invalidação após utilização.
8. Verificar se token aparece em logs.
9. Verificar se token aparece em respostas da API.
10. Verificar alteração efetiva da senha.
11. Verificar comportamento das sessões existentes após alteração da senha.
12. Verificar mensagens de erro para não revelar se um email existe.

Não enviar emails reais.

### Arquitetura de email

Preparar a aplicação para utilizar um serviço transacional externo através de uma abstração, por exemplo:

`EmailService`

O código de autenticação não deve ficar diretamente acoplado à Brevo.

A arquitetura deve permitir futuramente:

`VORIXA -> EmailService -> Brevo`

e, se necessário, trocar o provider posteriormente sem reescrever a autenticação.

### Brevo

Não é necessário configurar credenciais reais da Brevo agora.

Criar apenas a estrutura necessária para futura integração, se isso não exigir alterações desnecessárias.

Não colocar API key real no código.

Não enviar email real.

# 3. MÚLTIPLOS MÉTODOS DE LOGIN

O VORIXA deve suportar:

1. Email + senha
2. Google

E deve permanecer preparado para futuros provedores OAuth.

### Verificar

- Credentials permanece funcional.
- Google permanece como provider independente.
- A arquitetura não deve assumir que Google será o único login social.
- Providers futuros devem poder ser adicionados sem reescrever o núcleo da autenticação.
- A identidade do usuário deve continuar sendo controlada pelo backend.
- Não permitir que o frontend escolha ou manipule arbitrariamente o provider para alterar identidade.

Não implementar outros providers agora.
