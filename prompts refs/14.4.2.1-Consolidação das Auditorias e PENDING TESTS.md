# 1. REGRA FUNDAMENTAL DE CLASSIFICAÇÃO

A partir desta auditoria, NÃO usar "aprovado" como sinônimo de "tudo foi testado".

Cada item deve possuir exatamente uma classificação principal:

### TESTADO

O comportamento foi efetivamente executado/testado no ambiente e existe evidência.

### INSPECIONADO

O código, configuração ou arquitetura foi analisado, mas o comportamento não pôde ser efetivamente executado.

### NÃO APLICÁVEL

O vetor realmente não existe no escopo atual do projeto.

A justificativa deve explicar por que não existe.

### PENDENTE

O teste ou validação precisa ser realizado posteriormente.

Exemplos:

- depende de produção;
- depende de credencial real;
- depende de domínio;
- depende de webhook público;
- depende de integração ainda não configurada;
- depende de infraestrutura futura;
- depende de funcionalidade ainda não implementada.

---

# 2. REGRA CONTRA FALSA APROVAÇÃO

Não converter:

`INSPECIONADO` → `TESTADO`

sem executar o teste.

Não converter:

`PENDENTE` → `CONCLUÍDO`

sem evidência.

Não converter:

`NÃO APLICÁVEL` → `TESTADO`

sem necessidade.

Não inventar testes retroativamente.

Se uma auditoria anterior usou uma classificação mais forte do que a evidência realmente suporta, corrigir a classificação no relatório consolidado.

NÃO alterar artificialmente os relatórios históricos apenas para parecer que tudo foi testado.

## REGRA PERMANENTE

O arquivo é cumulativo.

Nunca remover uma pendência simplesmente porque ela foi analisada.

Quando uma pendência for resolvida:

- manter o histórico;
- alterar status para `CONCLUÍDO`;
- registrar data;
- registrar fase;
- registrar auditoria;
- registrar evidência.

# 10. MIGRAR PENDÊNCIAS EXISTENTES

Todas as pendências encontradas durante as auditorias anteriores devem ser registradas no `PENDING_TESTS.md`.

Especialmente:

- testes dependentes de ambiente de produção;
- integrações externas ainda não homologadas;
- OAuth real;
- Brevo real;
- fal.ai live;
- webhooks públicos;
- gateway de pagamento;
- Cloudflare/R2 em produção;
- domínio/HTTPS;
- timeout de downloads;
- limite de tamanho de download;
- qualquer item anteriormente classificado como `NÃO FOI POSSÍVEL TESTAR`;
- qualquer item que permaneça somente `INSPECIONADO` e que mereça validação posterior.

Não inventar pendências.

Não transformar toda inspeção em pendência se não houver benefício de um teste futuro.

`docs/DEVELOPMENT_RULES.md`

ou o arquivo equivalente existente.

Adicionar uma regra permanente:

## PENDING TESTS OBRIGATÓRIO

Antes de iniciar uma nova fase ou auditoria:

1. consultar `docs/PENDING_TESTS.md`;
2. verificar se existe pendência relacionada à etapa atual;
3. executar pendências que já possam ser validadas;
4. acrescentar novas pendências encontradas;
5. preservar o histórico;
6. nunca apagar itens sem evidência de conclusão.

Ao finalizar qualquer fase ou auditoria:

1. revisar o arquivo;
2. adicionar novas pendências;
3. atualizar itens realmente concluídos;
4. registrar evidências;
5. informar no relatório final o que foi adicionado ou concluído.
