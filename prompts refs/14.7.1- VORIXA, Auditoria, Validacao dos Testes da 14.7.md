# VORIXA, AUDITORIA 14.7.1: VALIDAÇÃO DOS TESTES DA AUDITORIA 14.7

## OBJETIVO
Auditar os próprios testes criados/executados na Auditoria 14.7. O objetivo é descobrir se os `47/47 testes aprovados` realmente comprovam os controles ou se existe falso positivo.

NÃO iniciar a Auditoria 14.8. NÃO executar outras auditorias.

## REGRA PRINCIPAL
`PASS` no Vitest não significa automaticamente que o controle está validado.

Para cada teste verificar:
1. Executa código real de produção?
2. Reproduz o cenário de ataque?
3. O `expect/assert` comprova a propriedade correta?
4. O mock pode esconder a vulnerabilidade?
5. Se a proteção fosse removida, o teste falharia?
6. Existe resultado observável?
7. O teste verifica comportamento, não apenas configuração?

Não alterar testes apenas para fazê-los passar.

## 1. IDENTIFICAR OS TESTES DA 14.7
Localizar testes relacionados à 14.7, especialmente `auth.test.ts`, `__tests__/` e `tests/`.

Para cada teste registrar:
- nome;
- arquivo;
- função de produção exercitada;
- mocks;
- assertions.

## 2. CONTAGEM REAL
Confirmar se `47/47 testes` corresponde realmente à quantidade de testes executados pelo Vitest. Não confundir testes, assertions, suites ou casos parametrizados.

## 3. AUTH-01, OPEN REDIRECT
Auditar o teste de Open Redirect. Não considerar suficiente apenas verificar `pages.signIn === "/login"`.

Testar, quando tecnicamente possível:
```text
https://evil.example
//evil.example
https://evil.example/path
```
Verificar se destinos externos são rejeitados ou neutralizados. Não executar JavaScript nem payload perigoso.

## 4. REGRESSÃO DO OPEN REDIRECT
Criar teste controlado que demonstre que a proteção é necessária. Quando seguro, alterar temporariamente a condição para uma configuração insegura e confirmar que o teste detectaria a regressão. Depois restaurar tudo.

Não deixar código vulnerável no repositório. Se não for possível, explicar e classificar como INSPECIONADO.

## 5. AUTH-03, ACCOUNT LINKING
Auditar `allowDangerousEmailAccountLinking: false`.

Verificar se o teste realmente falharia se fosse `true`. Não basta verificar que a propriedade existe.

Se apenas verifica configuração, classificar como `INSPECIONADO`.

## 6. ENUMERAÇÃO DE E-MAIL
Testar `/api/auth/recovery-password` com:
A) e-mail cadastrado;
B) e-mail inexistente.

Comparar status, JSON, mensagem, campos e headers. Tempo só quando mensurável de forma útil.

O atacante não deve conseguir diferenciar contas por resposta.

## 7. REGRESSÃO DA ENUMERAÇÃO
Confirmar que o teste falharia se o endpoint voltasse a retornar `404` para e-mail inexistente.

## 8. RECOVERY TOKEN
Auditar `AUTH-05`. Não marcar como TESTADO se Brevo não estiver integrado, token real não estiver persistido ou expiração real não estiver validada. Manter `PENDENTE` se depender de integração real.

## 9. GOOGLE OAUTH
Auditar `AUTH-02`. Confirmar que teste local não seja apresentado como OAuth real. Se não houver login real contra Google, manter `PENDENTE`.

## 10. MOCKS
Para cada teste identificar mocks e perguntar: o mock substitui justamente a parte que deveria ser testada?

Se mock esconder comportamento crítico, classificar como INSPECIONADO ou PENDENTE.

## 11. ASSERTIONS
Verificar cada `expect/assert`. Não considerar forte uma assertion genérica como `toBeDefined()` quando a segurança exige um comportamento específico.

## 12. TESTE NEGATIVO E POSITIVO
Quando possível, verificar ambos:
- Negativo: ataque/condição inválida é bloqueado.
- Positivo: fluxo legítimo continua funcionando.

## 13. PENDING_TESTS
Consultar `docs/PENDING_TESTS.md`. Não remover pendências sem evidência.

Confirmar que continuam registradas:
- Google OAuth real;
- recuperação real/Brevo;
- outras pendências relacionadas.

Executar:
```bash
npm test
```
ou equivalente, registrando `X/X testes aprovados`.

Depois:
```bash
npm run build
```

Não declarar aprovação somente porque o Vitest apresentou PASS.
