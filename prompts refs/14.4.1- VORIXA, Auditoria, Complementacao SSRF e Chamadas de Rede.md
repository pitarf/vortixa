# VORIXA, AUDITORIA 14.4.1: COMPLEMENTAÇÃO SSRF E CHAMADAS DE REDE

## OBJETIVO

Complementar exclusivamente a Auditoria 14.4.

A Auditoria 14.4 classificou SSRF como `NÃO APLICÁVEL`, porém precisamos comprovar de forma mais rigorosa todas as chamadas de rede realizadas no backend, especialmente porque o VORIXA trabalha com fal.ai, uploads, outputs e arquivos de mídia.

NÃO iniciar a Auditoria 14.5.

NÃO executar outras auditorias.

Executar somente esta complementação.

---

# REGRA OBRIGATÓRIA DE EXECUÇÃO

Não fazer apenas uma busca superficial.

Mapear todas as operações de rede server-side existentes no projeto.

Classificar cada ocorrência como:

- `TESTADO`
- `INSPECIONADO`
- `NÃO APLICÁVEL`
- `NÃO FOI POSSÍVEL TESTAR`

Não inventar evidências.

Não declarar SSRF inexistente apenas porque não encontrou `axios`.

Não considerar somente `fetch` e `axios`.

Pesquisar também SDKs, bibliotecas e funções que possam realizar requisições HTTP internamente.

Se encontrar vulnerabilidade, registrar o comportamento antes da correção e criar teste de regressão após a correção.

---

# 1. INVENTÁRIO DE CHAMADAS DE REDE

Pesquisar em todo o backend por:

- `fetch`
- `axios`
- `http`
- `https`
- `request`
- `got`
- `undici`
- `URL`
- `URLSearchParams`
- SDKs de terceiros que realizem chamadas HTTP
- funções de download
- funções de upload
- clientes de storage
- chamadas da fal.ai
- webhooks
- callbacks
- qualquer wrapper interno de rede

Também pesquisar por bibliotecas instaladas no `package.json` que possam realizar comunicação externa.

Para cada ocorrência encontrada, registrar:

- arquivo;
- função;
- finalidade;
- destino;
- se o destino é fixo ou controlável pelo usuário;
- se existe validação;
- se existe autenticação;
- se existe possibilidade de redirecionamento;
- se existe possibilidade de acesso a IP privado.

---

# 2. ENTRADAS CONTROLADAS PELO USUÁRIO

Identificar todas as entradas que possam influenciar URLs ou destinos de rede.

Pesquisar campos como:

- `url`
- `uri`
- `source`
- `imageUrl`
- `videoUrl`
- `audioUrl`
- `callbackUrl`
- `webhookUrl`
- `redirectUrl`
- `downloadUrl`
- `fileUrl`
- `inputUrl`

Também procurar campos com nomes diferentes que semanticamente representem uma URL.

Determinar se qualquer valor vindo do usuário consegue chegar a uma operação de rede server-side.

---

# 3. TESTE SSRF DIRETO

Se existir qualquer endpoint que aceite URL controlável pelo usuário e que posteriormente seja acessada pelo servidor, testar de forma segura URLs representativas de:

- `http://127.0.0.1`
- `http://localhost`
- `http://[::1]`
- `http://0.0.0.0`
- endereços de rede privada RFC1918;
- endereços link-local.

Não realizar exploração destrutiva.

O objetivo é somente verificar se o backend tenta acessar o destino.

---

# 4. REDIRECT SSRF

Se houver mecanismo de download por URL:

Verificar se o servidor segue redirects.

Testar, de forma controlada, cenário:

```text
URL pública
   ↓
redirect
   ↓
localhost/rede privada
```

Se o mecanismo não aceita URLs externas controladas pelo usuário, registrar `NÃO APLICÁVEL` com evidência.

---

# 5. FAL.AI

Auditar especificamente a integração com fal.ai.

Localizar:

- chamadas do SDK;
- upload;
- submit de Jobs;
- URLs de arquivos;
- callbacks;
- webhooks;
- downloads;
- outputs.

Determinar se qualquer URL fornecida pelo usuário é enviada à fal.ai de forma que possa provocar uma requisição server-side para um destino arbitrário.

Diferenciar claramente:

```text
URL enviada como parâmetro para API externa
```

de:

```text
VORIXA acessando a URL diretamente
```

Se o SDK da fal.ai puder buscar uma URL fornecida pelo usuário, verificar se isso cria um vetor de SSRF indireto e documentar o risco.

Não realizar exploração contra infraestrutura externa.

---

# 6. STORAGE E DOWNLOADS

Auditar especificamente:

- `StorageService`;
- `fal.storage`;
- Cloudflare R2;
- storage local;
- uploads;
- downloads de outputs;
- qualquer função que baixe arquivos.

Determinar se existe:

```text
URL controlada pelo usuário
        ↓
servidor VORIXA
        ↓
download HTTP
```

Se existir, testar validação e restrições.

Se não existir, comprovar no relatório.

---

# 7. WEBHOOKS

Localizar todos os webhooks.

Verificar se:

- URL do webhook é fixa/configurada pelo servidor;
- usuário consegue definir destino;
- payload pode provocar callback arbitrário;
- existe alguma chamada de rede baseada em dados recebidos no webhook.

Não confundir:

```text
VORIXA recebe webhook
```

com:

```text
VORIXA faz requisição para URL controlada por terceiro
```

---

# 8. REDIRECIONAMENTOS HTTP

Pesquisar:

- `redirect()`;
- `NextResponse.redirect`;
- URLs construídas dinamicamente;
- parâmetros `next`;
- parâmetros `returnUrl`;
- parâmetros `callback`;
- parâmetros `redirect`.

Verificar se existe Open Redirect ou possibilidade de transformar o redirecionamento em vetor de SSRF/abuso de fluxo.

Se houver apenas redirect de navegador, classificar separadamente de SSRF.

---

# 9. DNS REBINDING / HOST VALIDATION

Somente se existir mecanismo que aceite URL externa fornecida pelo usuário.

Verificar se a aplicação:

- resolve hostname;
- valida IP;
- permite localhost;
- permite IP privado;
- segue redirect;
- revalida destino após redirect.

Não implementar proteção complexa se não houver superfície vulnerável.

---

# 10. CREDENCIAIS E HEADERS

Verificar se requisições externas podem encaminhar acidentalmente:

- cookies;
- Authorization;
- tokens;
- API keys;
- headers internos;
- credenciais da fal.ai;
- credenciais do storage.

Especialmente importante caso exista download/proxy de URL externa.

Nenhuma credencial interna deve ser enviada para destino controlado pelo usuário.

---

# 11. PROXY OU ENDPOINT DE DOWNLOAD

Pesquisar se existe qualquer endpoint que funcione como:

```text
GET /api/download?url=...
```

ou equivalente.

Se existir:

1. testar URL externa;
2. testar localhost;
3. testar IP privado;
4. testar redirect;
5. verificar validação;
6. verificar resposta;
7. verificar headers;
8. verificar vazamento de credenciais.

Se não existir, registrar evidência concreta.

---

# 12. TESTES DE REGRESSÃO

Se existir superfície SSRF, criar testes específicos.

Se não existir, criar pelo menos testes que garantam que endpoints atuais não aceitam URL arbitrária onde não deveriam.

Testar, quando aplicável:

1. localhost;
2. loopback;
3. IP privado;
4. link-local;
5. URL externa;
6. redirect;
7. URL malformada;
8. protocolo não permitido;
9. URL com credenciais embutidas.

Não realizar testes destrutivos.

---

# 13. BUILD E REGRESSÃO

Executar toda a suíte de testes existente.

Registrar:

- quantidade total;
- quantidade aprovada;
- quantidade falha.

Executar:

```bash
npm run build
```

Registrar resultado.

Nenhum teste anterior pode regredir.
