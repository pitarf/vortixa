# VORIXA, AUDITORIA 14.8.1: RATE LIMITING E PROTEÇÃO CONTRA ABUSO

## OBJETIVO

Complementar exclusivamente a Auditoria 14.8.

A Auditoria 14.8 identificou que o VORIXA atualmente não possui rate limiting programático na aplicação e que a proteção foi planejada para infraestrutura de borda, como Nginx/Cloudflare, com Redis em fase futura.

Esta etapa deve definir e preparar a proteção corretamente, sem fingir que ela já está homologada.

NÃO iniciar a Auditoria 14.9.

## REGRA PRINCIPAL

Não considerar rate limiting como TESTADO apenas porque existe documentação ou configuração.

Classificar:
- TESTADO: comportamento realmente executado e comprovado;
- INSPECIONADO: análise de código/configuração;
- NÃO APLICÁVEL: justificativa técnica;
- PENDENTE: depende da VPS, Cloudflare, domínio ou infraestrutura real.

## 1. MAPEAR ENDPOINTS SENSÍVEIS

Considerar pelo menos:
- login;
- recovery-password;
- upload;
- generate;
- job status/polling;
- config;
- webhooks;
- endpoints administrativos sensíveis.

Registrar quais precisam de proteção contra abuso.

## 2. DEFINIR LIMITES

Propor limites iniciais para:
- autenticação;
- recuperação de senha;
- upload;
- geração de IA;
- polling;
- APIs administrativas.

Para cada limite registrar quantidade, janela, chave de identificação, resposta, HTTP esperado e Retry-After quando aplicável.

Não afirmar que esses limites já estão ativos.

## 3. IP E PROXY

Definir política segura para Nginx, Cloudflare, X-Forwarded-For e X-Real-IP.

O cliente não pode controlar diretamente a identidade usada para rate limiting.

Documentar qual camada será autoridade para o IP.

Não confiar cegamente em X-Forwarded-For recebido diretamente da internet.

## 4. RATE LIMITING NA BORDA

Documentar a configuração planejada para a VPS: onde aplicar, rotas, limites, burst, comportamento, resposta HTTP e logs.

Se Nginx/Cloudflare não estiver disponível agora, classificar homologação como PENDENTE.

Não afirmar que foi testado.

## 5. HTTP 429

Definir comportamento esperado quando exceder o limite:

HTTP 429 Too Many Requests

Avaliar Retry-After.

Se não puder testar agora, deixar PENDENTE.

## 6. ABUSO DE GERAÇÃO DE IA

Confirmar que rate limiting é camada adicional e não substitui:
- autenticação;
- ownership;
- idempotência;
- controle de créditos;
- concorrência;
- limite de input.

## 7. UPLOAD

Confirmar combinação com:
- limite de tamanho;
- validação de tipo;
- autenticação;
- ownership;
- storage seguro.

## 8. POLLING

Definir limite para /api/tools/job/[id], evitando polling abusivo sem quebrar o frontend legítimo.

## 9. TESTE DE SPOOFING

Criar testes locais ou preparatórios para X-Forwarded-For e X-Real-IP.

Comprovar que a aplicação não deve confiar cegamente nesses headers quando chegam diretamente do cliente.

Se depender de Nginx/Cloudflare, classificar como PENDENTE e registrar o teste necessário para a VPS.

## 10. TESTES DE REGRESSÃO

Criar testes apenas para regras verificáveis localmente.

Não simular falsamente que Nginx ou Cloudflare existem.

## 11. PENDING_TESTS

Atualizar:

docs/PENDING_TESTS.md

Manter pendências para:
- rate limiting real na VPS;
- Cloudflare/WAF;
- Nginx;
- IP confiável;
- HTTP 429;
- burst;
- bypass via X-Forwarded-For.

NÃO remover pendências existentes sem evidência real.

## 12. REDIS

Não implementar Redis nesta etapa apenas para satisfazer a auditoria.

A arquitetura futura com Redis permanece como fase de crescimento.

## 13. TESTES E BUILD

Executar:

npm test

Registrar a quantidade exata de testes aprovados.

Depois:

npm run build

Registrar o resultado.

Não afirmar que infraestrutura de produção foi testada se não foi.
