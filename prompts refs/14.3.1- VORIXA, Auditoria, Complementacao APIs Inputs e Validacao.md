# 3. LIMITE DE TAMANHO DE PROMPT

A Auditoria 14.3 informou que prompts gigantes foram processados sem travamento.

Agora determinar se existe limite de tamanho no backend.

Pesquisar:

- Zod;
- limites de string;
- body parser;
- limites de request;
- middleware;
- reverse proxy quando aplicável;
- limites específicos das ferramentas.

### Testes controlados

Testar prompts progressivamente maiores, por exemplo:

- 1.000 caracteres;
- 5.000;
- 10.000;
- 25.000;
- 50.000;
- 100.000;

Não realizar testes destrutivos.

Determinar:

1. qual é o limite atual;
2. onde ele é aplicado;
3. se é aplicado no backend;
4. se o frontend possui limite diferente;
5. o que acontece quando o limite é excedido;
6. se existe risco de consumo excessivo de memória/CPU;
7. se o request pode atingir a fal.ai antes da validação.

### Regra

A proteção não pode depender exclusivamente do frontend.

Se não houver limite backend, registrar como vulnerabilidade/recomendação de segurança e propor um limite apropriado.

Não implementar limite arbitrário sem justificar tecnicamente.

# 5. RELAÇÃO TOOL ↔ MODEL

A Auditoria 14.3 marcou VAL-14 como `TESTADO`, porém a evidência apresentada foi principalmente uma inspeção do relacionamento Prisma.

Agora validar o comportamento através da API.

### Teste

1. Identificar Tool A e Model A válidos.
2. Identificar Tool B e Model B válidos.
3. Tentar gerar utilizando Tool A com Model B, quando a API aceitar qualquer identificador de modelo.
4. Tentar alterar `modelId`.
5. Tentar alterar `modelSlug`.
6. Tentar alterar qualquer campo equivalente.
7. Tentar enviar um modelo inexistente.
8. Tentar enviar modelo desativado.

### Esperado

O backend deve determinar a relação válida entre Tool e Model a partir da configuração confiável do banco.

O cliente não pode escolher arbitrariamente um modelo diferente daquele configurado para a ferramenta.

Se a API não aceitar `modelId`/`modelSlug` diretamente, registrar como `NÃO APLICÁVEL` e demonstrar no código que a relação é determinada exclusivamente pelo servidor.

# 6. MANIPULAÇÃO DO CUSTO

Este é um teste crítico para o VORIXA.

O custo da geração NÃO pode ser definido pelo cliente.

Pesquisar e testar possíveis campos:

- `creditCost`;
- `credits`;
- `cost`;
- `price`;
- `amount`;
- `billingUnit`;
- `billingQuantity`;
- `providerCostUsd`;
- `creditsCharged`;
- `creditsReserved`;
- equivalentes.

### Testes

Enviar valores forjados, por exemplo:

```json
{
  "creditCost": 0,
  "credits": 0,
  "price": 0,
  "amount": 0
}
```

E também valores extremamente altos.

### Esperado

O backend deve ignorar ou rejeitar esses valores.

O custo deve ser calculado exclusivamente a partir da configuração confiável do VORIXA no servidor/banco.

O cliente nunca pode definir quantos créditos serão cobrados.
