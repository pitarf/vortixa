# VORIXA, AUDITORIA 14.5.1: COMPLEMENTAÇÃO CSRF, CORS E SECURITY HEADERS

## OBJETIVO

Complementar exclusivamente a Auditoria 14.5.

A auditoria anterior implementou Security Headers importantes, porém CSRF/CORS foram apenas `INSPECIONADOS` e os headers foram considerados `TESTADOS` principalmente pela implementação e build.

Agora precisamos validar o comportamento real.

NÃO iniciar a Auditoria 14.6.
NÃO executar outras auditorias.
Executar somente esta complementação.

## REGRA OBRIGATÓRIA

Diferenciar:
- `TESTADO`: comportamento executado e comprovado;
- `INSPECIONADO`: somente código/configuração analisado;
- `NÃO APLICÁVEL`: vetor inexistente;
- `PENDENTE`: depende de ambiente ou integração futura.

Não transformar inspeção em teste.
Não afirmar que CSRF está protegido apenas porque existe `SameSite=Lax`.
Não tratar CORS como substituto de proteção CSRF.
Não alterar testes para produzir aprovação artificial.

Se encontrar vulnerabilidade, registrar o comportamento antes da correção e criar teste de regressão depois.

## 1. MAPEAR ROTAS DE ALTERAÇÃO DE ESTADO

Localizar todas as rotas POST, PUT, PATCH e DELETE, especialmente:
- `/api/tools/generate`
- `/api/tools/upload`
- `/api/tools/*`
- autenticação;
- recuperação de senha;
- alterações de perfil;
- créditos;
- pagamentos;
- rotas administrativas existentes.

Registrar autenticação, método, cookies, proteção CSRF, validação de Origin/Referer e possibilidade de requisição cross-site.

## 2. TESTE REAL DE CSRF

Executar testes HTTP reais contra rotas de alteração de estado.

Criar cenário equivalente a:

Atacante: `https://evil.example`
        ↓
POST cross-site
        ↓
`https://VORIXA/api/tools/generate`

Verificar se uma sessão autenticada poderia ser utilizada para executar a ação.

Registrar origem, endpoint, método, headers, cookies, status e se o estado foi alterado.

## 3. SAME-SITE

Verificar configuração real do Auth.js:
- SameSite;
- Secure;
- HttpOnly;
- domínio;
- path;
- cookies de sessão;
- cookies CSRF.

Confirmar comportamento same-origin, same-site e cross-site.

Documentar exatamente o que SameSite protege.

## 4. ORIGIN / REFERER

Verificar se endpoints de alteração de estado validam Origin/Referer quando apropriado.

Se não validarem, registrar claramente e avaliar necessidade de defesa adicional.

## 5. CSRF TOKEN

Verificar como `authjs.csrf-token` é usado.

Diferenciar proteção das rotas internas do Auth.js da proteção das rotas de negócio do VORIXA.

Verificar se `/api/tools/generate` e outras rotas de negócio possuem proteção CSRF própria.

## 6. GERAÇÃO DE IA

Testar se um atacante poderia provocar `POST /api/tools/generate` utilizando sessão da vítima.

Testar payload válido, inválido, ausência de token, Origin externo e Referer externo.

Não executar carga elevada.

## 7. UPLOAD

Testar `/api/tools/upload` contra CSRF.

Verificar se página externa consegue induzir upload autenticado e registrar alteração de estado, consumo de recursos e status.

## 8. CORS REAL

Executar testes HTTP reais com:
`Origin: https://evil.example`
e
`Origin: https://example.com`

Verificar:
- Access-Control-Allow-Origin;
- Access-Control-Allow-Credentials;
- Access-Control-Allow-Methods;
- Access-Control-Allow-Headers;
- OPTIONS;
- POST.

Não basta procurar headers no código.

## 9. PREFLIGHT

Testar OPTIONS reais.

Verificar se não libera origens arbitrárias, credenciais indevidas ou métodos perigosos.

## 10. SECURITY HEADERS VIA HTTP REAL

Não considerar `next.config.ts` como evidência suficiente.

Fazer requests HTTP reais, quando acessível, para `/`, `/login` e `/dashboard`.

Verificar valores efetivamente recebidos de:
- X-Frame-Options
- Content-Security-Policy
- X-Content-Type-Options
- Referrer-Policy
- Strict-Transport-Security

## 11. CLICKJACKING

Testar presença real de:
`X-Frame-Options: DENY`
e
`Content-Security-Policy: frame-ancestors 'none'`

## 12. CSP

Localizar a CSP completa entregue pelo sistema.

Se houver apenas `frame-ancestors 'none'`, registrar exatamente isso.

Não criar CSP abrangente automaticamente nesta auditoria.

## 13. HSTS

Verificar valor real de:
`Strict-Transport-Security`

Confirmar max-age, includeSubDomains e preload.

Se depender de HTTPS/VPS/domínio real, classificar como `PENDENTE`.

## 14. HTTPS

Diferenciar HTTP local, HTTPS staging e HTTPS produção.

Não afirmar homologação de HTTPS sem ambiente testável.

## 15. HEADERS ADICIONAIS

Verificar, sem implementar automaticamente:
- Permissions-Policy;
- Cross-Origin-Opener-Policy;
- Cross-Origin-Resource-Policy;
- Cross-Origin-Embedder-Policy;
- Cache-Control em respostas sensíveis.

## 16. REGRESSÃO

Executar toda a suíte existente.

Adicionar testes para:
1. CSRF em `/api/tools/generate`;
2. CSRF em `/api/tools/upload`;
3. Origin externo;
4. CORS externo;
5. OPTIONS/preflight;
6. Security Headers;
7. ausência de `Access-Control-Allow-Origin: *`;
8. cookies de sessão;
9. HSTS quando aplicável.

Nenhum teste anterior pode regredir.

## 17. PENDING_TESTS

Consultar obrigatoriamente `docs/PENDING_TESTS.md`.

Se algo depender de domínio real, HTTPS, VPS, Google OAuth, Brevo, webhook público ou fal.ai live, não marcar como TESTADO.

Registrar/atualizar a pendência.

Nunca remover pendências sem evidência de conclusão.

## 18. BUILD

Executar:
```bash
npm run build
```

Executar também a suíte completa e registrar quantidade exata de testes aprovados.

Não utilizar "100% de cobertura".
