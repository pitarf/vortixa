# VORIXA, AUDITORIA 14.6.1: COMPLEMENTAÇÃO DE VAZAMENTO DE SECRETS

## OBJETIVO

Complementar exclusivamente a Auditoria 14.6, validando canais adicionais de vazamento:

1. respostas HTTP/API;
2. mensagens de erro;
3. logs;
4. artefatos reais do build `.next`;
5. source maps, quando existirem.

NÃO iniciar a Auditoria 14.7.
NÃO executar outras auditorias.
NÃO alterar a arquitetura sem necessidade.

## REGRA

Classificar cada item como:
- `TESTADO`: comportamento efetivamente executado e comprovado;
- `INSPECIONADO`: somente análise de código/configuração;
- `NÃO APLICÁVEL`: vetor inexistente, com justificativa;
- `PENDENTE`: depende de ambiente ou integração futura.

Não transformar inspeção em teste. Não inventar evidências. Não declarar "100% seguro".

Se encontrar vazamento real, corrigir e criar teste de regressão.

## 1. INVENTÁRIO

Levantar nomes das credenciais atuais sem expor valores reais, incluindo quando existentes:
- `FAL_KEY`
- `DATABASE_URL`
- `AUTH_SECRET`
- `GOOGLE_CLIENT_SECRET`
- `VOREXPAY_API_KEY`
- `VOREXPAY_WEBHOOK_SECRET`
- credenciais Brevo
- credenciais Cloudflare/R2
- outras variáveis sensíveis do `.env.example`

## 2. RESPOSTAS HTTP

Subir a aplicação em build apropriado e realizar requisições HTTP reais às rotas acessíveis, priorizando:
- `/api/tools/config`
- `/api/tools/generate`
- `/api/tools/upload`
- `/api/tools/job/[id]`
- `/api/auth/*`
- endpoints administrativos existentes
- webhooks existentes

Testar respostas de sucesso e erro controlado.

Procurar por:
- nomes ou valores de secrets;
- connection strings;
- tokens;
- Authorization;
- API keys;
- passwords;
- URLs internas sensíveis.

Não enviar secrets reais nos requests.

## 3. ERROS

Provocar erros controlados:
- JSON inválido;
- campos ausentes;
- IDs inexistentes;
- payload inválido;
- autenticação ausente;
- ferramenta inexistente;
- erro controlado de integração.

Verificar se são expostos:
- stack trace;
- caminhos absolutos;
- SQL;
- DATABASE_URL;
- API keys;
- tokens;
- headers internos;
- detalhes desnecessários de infraestrutura.

Se houver vazamento, corrigir.

## 4. LOGS

Inspecionar e, quando possível, executar cenários de erro para verificar logs reais.

Procurar:
- `console.log`
- `console.error`
- `console.warn`
- logger utilizado;
- logs Prisma;
- logs fal.ai;
- logs VorexPay;
- logs de autenticação.

Verificar se secrets, tokens ou headers completos podem ser registrados.

Não imprimir secrets reais durante os testes.

## 5. STACK TRACE

Verificar respostas HTTP de erro em produção/build de produção.

Confirmar:
- stack trace não chega ao cliente;
- caminhos internos não são expostos desnecessariamente;
- mensagens internas não revelam secrets.

Não considerar somente development como evidência.

## 6. ARTEFATOS `.next`

Executar:

```bash
npm run build
```

Inspecionar `.next/`.

Pesquisar pelos nomes das variáveis:
- `FAL_KEY`
- `DATABASE_URL`
- `AUTH_SECRET`
- `GOOGLE_CLIENT_SECRET`
- `VOREXPAY_API_KEY`
- `VOREXPAY_WEBHOOK_SECRET`

Pesquisar também valores sensíveis quando possível, sem expô-los no relatório.

Verificar client chunks, server chunks, manifests, assets, runtime e source maps.

A presença do nome da variável não é automaticamente vazamento. Determinar se o valor real aparece.

## 7. SOURCE MAPS

Procurar arquivos `*.map`.

Se existirem:
- verificar se incluem código server-side;
- verificar secrets;
- verificar valores de ambiente;
- verificar se são públicos ou somente internos.

## 8. CLIENT BUNDLE

Inspecionar diretamente os arquivos enviados ao navegador, especialmente `.next/static/`.

Procurar:
- valores reais de secrets;
- `process.env`;
- connection strings;
- JWT secrets;
- API keys;
- Authorization headers;
- credenciais.

## 9. SERVER BUNDLE

Inspecionar artefatos server.

A presença de secrets em código exclusivamente server-side não é, por si só, vazamento.

Verificar se existe caminho para o valor chegar ao client.

## 10. SERIALIZAÇÃO

Procurar situações como:
- retorno de `process.env`;
- retorno de objetos de configuração contendo secrets;
- serialização de objetos de erro;
- objetos de provider;
- respostas de serviços externos.

O objetivo é impedir vazamento acidental por serialização.

## 11. HEADERS HTTP

Verificar se respostas expõem:
- Authorization;
- cookies indevidos;
- API keys;
- headers internos;
- infraestrutura sensível.

Confirmar também que erros não ecoam headers sensíveis.

## 12. TESTES DE REGRESSÃO

Adicionar testes quando tecnicamente aplicável para:
1. API não retornar secret;
2. erro não retornar secret;
3. erro não retornar stack trace;
4. endpoint não serializar `.env`;
5. client bundle não conter valor secreto;
6. logs não registrarem secret completo.

Não criar testes artificiais.

## 13. PENDING_TESTS

Consultar `docs/PENDING_TESTS.md`.

Se depender de produção, domínio, HTTPS, proxy, Cloudflare, Brevo, VorexPay, fal.ai live ou R2, classificar como `PENDENTE` se não puder ser executado agora.

Nunca remover pendência sem evidência.

## 14. TESTES E BUILD

Executar a suíte completa e registrar a quantidade exata:

```text
X/X testes aprovados
```

Depois:

```bash
npm run build
```

Registrar resultado.
