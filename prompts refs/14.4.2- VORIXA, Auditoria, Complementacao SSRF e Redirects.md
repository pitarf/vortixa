# VORIXA, AUDITORIA 14.4.2: VALIDAÇÃO DE REDIRECTS E SSRF

## OBJETIVO

Complementar exclusivamente a Auditoria 14.4.1.

A 14.4.1 implementou whitelist de hosts confiáveis no `StorageService`, porém a evidência do teste de redirects não foi suficiente para comprovar que um redirect não pode levar o servidor VORIXA para um destino interno.

Esta auditoria deve validar exclusivamente esse ponto.

NÃO iniciar a Auditoria 14.5.

NÃO executar outras auditorias.

---

# REGRA OBRIGATÓRIA DE EXECUÇÃO

Não assumir que a whitelist do hostname inicial protege automaticamente contra redirects.

É obrigatório verificar o comportamento real do mecanismo HTTP utilizado pelo VORIXA.

Classificar cada item como:

- `TESTADO`
- `INSPECIONADO`
- `NÃO APLICÁVEL`
- `NÃO FOI POSSÍVEL TESTAR`

Não inventar evidências.

Se uma falha for encontrada, registrar o comportamento antes da correção e criar teste de regressão depois.

Não remover testes existentes.

---

# 1. IDENTIFICAR O MECANISMO DE DOWNLOAD

Localizar exatamente a implementação usada pelo `StorageService` para baixar mídias.

Verificar:

- `fetch`;
- biblioteca HTTP utilizada;
- configuração de redirects;
- headers;
- timeout;
- tratamento de erros;
- validação do hostname.

Registrar arquivo e função responsáveis.

---

# 2. VERIFICAR COMPORTAMENTO DE REDIRECT

Determinar explicitamente:

- se redirects são seguidos automaticamente;
- se redirects são bloqueados;
- se existe `redirect: "manual"`;
- se existe limite de redirects;
- se o destino de cada redirect é validado.

Não considerar a análise da documentação da biblioteca como substituto do teste do comportamento da aplicação.

---

# 3. TESTE DE REDIRECT PARA LOCALHOST

Criar um teste controlado representando:

```text
https://dominio-confiavel.fal.ai/arquivo
              ↓
HTTP 302
              ↓
http://127.0.0.1:porta
```

O objetivo é comprovar que o servidor VORIXA não acessa o destino interno.

Não utilizar serviços externos reais.

Não realizar exploração contra infraestrutura de terceiros.

---

# 4. TESTE DE REDIRECT PARA LOOPBACK

Testar destinos representativos:

```text
http://127.0.0.1
http://localhost
http://[::1]
```

Confirmar que nenhum deles é acessado pelo servidor.

---

# 5. TESTE DE REDIRECT PARA REDE PRIVADA

Testar de forma controlada destinos como:

```text
http://192.168.1.1
http://10.0.0.1
http://172.16.0.1
```

O objetivo é comprovar que um redirect não permite alcançar redes privadas.

Não realizar chamadas reais contra redes que não pertençam ao ambiente de teste.

---

# 6. TESTE DE REDIRECT EM CADEIA

Se o mecanismo seguir redirects, testar conceitualmente:

```text
Host confiável
    ↓ 302
Outro host
    ↓ 302
127.0.0.1
```

Verificar se cada destino é validado.

Se a aplicação bloquear redirects completamente, registrar isso como comportamento seguro e testar a rejeição.

---

# 7. DECISÃO DE IMPLEMENTAÇÃO

Se o VORIXA atualmente seguir redirects automaticamente sem revalidar o destino:

Preferir a solução:

```text
redirect: "manual"
```

e rejeitar redirects não esperados.

Somente adotar outra estratégia se houver justificativa técnica documentada.

Não permitir que um redirect contorne a whitelist.

---

# 8. VALIDAÇÃO DA WHITELIST

Verificar novamente os domínios permitidos.

Confirmar que:

- apenas hosts realmente confiáveis são aceitos;
- subdomínios não intencionais não são aceitos;
- manipulação de hostname não permite bypass;
- URLs com usuário/senha embutidos não permitem bypass;
- portas arbitrárias não criam bypass;
- esquemas diferentes de HTTP/HTTPS não criam bypass;
- hostname semelhante ao domínio confiável não é aceito indevidamente.

Exemplos conceituais a verificar:

```text
fal.ai.evil.example
evil-fal.ai.example
fal.ai@evil.example
evil.example?redirect=fal.ai
```

Não usar esses exemplos como regra fixa de implementação. O objetivo é verificar a análise correta do hostname pela biblioteca URL.

---

# 9. CREDENCIAIS

Confirmar novamente que nenhum redirect ou download pode encaminhar:

- `FAL_KEY`;
- cookies;
- tokens de sessão;
- Authorization;
- secrets;
- headers internos.

Criar teste se necessário.

---

# 10. TIMEOUT E RECURSOS

Como parte da mesma análise de download, verificar se existe:

- timeout;
- limite de tamanho de resposta;
- tratamento de resposta muito grande;
- abort de requisição.

Se esses controles ainda não existirem, NÃO implementar automaticamente nesta auditoria se isso ampliar o escopo.

Registrar no arquivo de testes pendentes para implementação/validação posterior.

---

# 11. TESTES DE REGRESSÃO

Criar ou ampliar testes automatizados para:

1. redirect de host confiável para localhost;
2. redirect para 127.0.0.1;
3. redirect para localhost;
4. redirect para IPv6 loopback;
5. redirect para IP privado;
6. cadeia de redirects;
7. hostname malicioso parecido com host confiável;
8. URL com credenciais embutidas;
9. esquema inesperado;
10. ausência de vazamento de credenciais.

Executar toda a suíte existente.
